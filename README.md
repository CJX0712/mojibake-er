把一段已经烂掉的乱码，反推回它本来应该是什么字。

不是"猜编码"，是把乱码当成**案发现场**来查：先看症状，再枚举"它可能被怎么错读过一遍"，给出按可信度排序的若干套修复方案，并把每一步字节都摊开给你看。

单个 HTML 文件，双击即用。零依赖、零构建、**完全离线** —— 文本只在浏览器内存里，不联网、不上传、不留痕。

## 怎么用

下载 `index.html` → 双击打开 → 把乱码粘进去（或把 `.txt` 文件拖进虚线框）→ 点**开始诊断**。

也可以先点下面的示例按钮（锟斤拷 / `æµ‹è¯•` / `ä¸­æ–‡` 等 7 种），看看效果。

## 它到底在干什么

乱码的本质几乎都是同一件事：**字节没变，只是被人用错误的编码表读了一遍。**

```
原文  "中文"                     → UTF-8 字节  E4 B8 AD E6 96 87
误读  把上面这些字节当 GBK 读    → "涓枃"
修复  反向操作：用 GBK 把"涓枃"编码回字节，再用 UTF-8 解码
      → E4 B8 AD E6 96 87 → "中文"   ✓
```

所以"修复一步"的定义是：**用编码 A 把当前文本编码成字节，再用编码 B 把字节解码成文本**。真实世界里的乱码常常被错读了两三次（锟斤拷就是典型），所以这里做的是一个 **1~3 步的 beam search**：

- 编码表 14 种：UTF-8 / UTF-16LE / UTF-16BE / GB18030 / GBK / Big5 / Shift_JIS / EUC-JP / EUC-KR / Windows-1252 / Windows-1251 / KOI8-R / ISO-8859-2 / ISO-8859-7
- 每一步展开 14 × 14 种组合，beam 宽度 20，且刻意保留编码对多样化的候选，避免"中间态长得丑但其实是正确路径"被提前剪掉
- 每个结果用**人话评分**排序（见下），并叠加对"常见误读编码""修回 UTF-8"的先验加分，以及"步数越多越可疑"的奥卡姆惩罚

### 怎么判断一段文本"像不像人话"

这是整个工具的核心。评分 `scoreText()` 大致考虑：

| 维度 | 说明 |
|---|---|
| 汉字浓度 | 常用字命中率 + 汉字在**非噪音字符**中的占比（夹在中间的英文单词不稀释浓度） |
| 随机汉字识别 | 汉字 ≥ 5 个而常用字命中 < 25% → 重罚。乱码乱转最容易撞出"看起来像中文"的汉字串 |
| 其它文字 | 假名 / 谚文 / 西里尔 / 希腊字母，按其在全文中的**占比**加权给分，零星几个拿不到满分 |
| 脚本混写 | 中·日 与 韩·俄·希 同时出现 → 重罚。正常人类文本几乎不这么写 |
| 硬伤 | U+FFFD、控制字符、`?` 替换 —— 出现即几乎可以判定没修对 |
| 常见词 | 命中内置常用词表（中/俄）加分 |
| 西里尔全大写 | 编码乱转的产物常常是一片大写，正常俄文以小写为主 |

### 关于 U+FFFD（那个黑问号）

字节一旦被替换成 U+FFFD，**原始信息就已经丢了**，严格来说不可逆。但这个工具还是做了一个有节制的尝试：UTF-8 自身的结构（首字节决定后续字节数、续字节必须是 `10xxxxxx`）会反过来约束"这里原本可能是哪些字节"。当且仅当**最优结果里仍有 U+FFFD、且推断确实减少了损伤**时，才会启动这一步，并且明确标记为**推断值**、额外扣分 —— 宁可告诉你"这里是我猜的"，也不假装修好了。

## 七个面板

1. **接诊** —— 粘贴 / 拖入文件，选原文本语种、搜索深度
2. **症状** —— 锟斤拷、U+FFFD、Latin-1 特征、西里尔特征、问号替换、高位拉丁堆积
3. **诊断结果** —— 按可信度排序的候选方案，每个都给出评分理由和它用的编码链
4. **病因** —— 从原文到乱码，每一步字节经历了什么，完整链路重建
5. **字节解剖** —— hex dump，同一个字节在 14 种编码下分别被解释成什么
6. **手动修复** —— 自己指定"用 A 编码回字节，再按 B 解码"，实时预览
7. **报告** —— 导出 Markdown，含症状、候选、编码链与字节证据

## 局限

- **问号替换不可逆。** 原始字符在目标编码里不存在被写成 `?` 之后，信息就真的没了，只能靠上下文人肉补
- **奇数字节的双字节误读会丢尾巴。** 比如 UTF-8 韩文（30 字节）被当 GBK 读成 15 个字，再编码回去时字节数对不齐，最后一个字符可能被截断
- **浏览器只原生提供 UTF-8 的编码器。** 其它 13 种编码的"字符 → 字节"反向表是启动时用 `TextDecoder` 枚举字节序列反查出来的，个别编码的极少数字符可能查不到
- 它给的是**排序后的候选**，不是唯一真理。第 3 名也可能是对的 —— 尤其当原文混了多种语言时
